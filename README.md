# Video / Audio Telegram Bot

Java 17, Spring Boot 3.5, Hibernate, PostgreSQL, Flyway, S3, FFmpeg и OpenAI `gpt-4o-transcribe-diarize`. Redis и отдельный брокер не нужны.

Бот принимает видео, аудио, голосовые сообщения, видеокружки и документы с аудиодорожкой. Возвращает одно сообщение: UTF-8 TXT с говорящими и таймкодами (имя файла — по первым двум репликам) и подписью со встроенной ссылкой S3 и датой окончания доступа. Статус обновляется в одном сообщении.

Повторно отправленный файл (тот же `file_unique_id` от того же пользователя в том же чате) не обрабатывается: бот отвечает на исходное сообщение с результатом. Если прошлая задача завершилась `FAILED`, повторная отправка создаёт новую задачу.

## Запуск

Клонируйте два репозитория в соседние каталоги:

```sh
git clone git@github.com:yanisderbikov/video-audio-bot.git
git clone git@github.com:yanisderbikov/local-server-telegram-bot.git
cd video-audio-bot
cp .env.example .env
```

Заполните `.env`:

| Переменная | Назначение |
|---|---|
| `DB_PASSWORD` | Пароль PostgreSQL |
| `TELEGRAM_BOT_TOKEN` | Токен BotFather |
| `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` | Данные Telegram приложения для Local API |
| `OPENAI_API_KEY` | Ключ с доступом к модели диаризации |
| `S3_BUCKET` | Уже созданный закрытый bucket |
| `S3_ENDPOINT`, `S3_REGION` | Endpoint и регион S3-провайдера; для AWS endpoint можно оставить пустым |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Доступ к S3; пустые значения включают стандартную AWS credential chain |
| `S3_PUBLIC_ENDPOINT` | Внешний адрес для подписанных ссылок, если отличается от внутреннего endpoint |
| `TELEGRAM_ALLOWED_USER_IDS` | Telegram user ID через запятую; пусто — бот принимает всех |

Полный список настроек и значения по умолчанию — в `.env.example`. Для обычного запуска достаточно обязательных ключей. Переменные читаются непосредственно из окружения; Spring Boot сам не читает `.env`, это делает Docker Compose.

```sh
docker compose up -d --build
docker compose logs -f app
curl http://localhost:8080/actuator/health
```

Compose запускает PostgreSQL, Local Bot API и Java-приложение. S3 используется внешний. Первая компиляция Local API/TDLib занимает время и требует нескольких ГБ RAM. `LOCAL_BOT_BUILD_JOBS=1` уменьшает нагрузку сборки. По умолчанию транскрибация ограничена 12 часами и входной файл — 2 ГиБ; ограничения настраиваются env.

Без общего volume (например, Railway) задайте `TELEGRAM_FILE_SERVER_URL` (адрес файлового сервера Local API, порт 8082) и `TELEGRAM_FILE_SERVER_TOKEN` (тот же, что `FILE_SERVER_TOKEN` у Local API). Тогда файлы скачиваются и удаляются по HTTP, `TELEGRAM_LOCAL_DIRECTORY` не используется.

Образ Java собирается без тестов, поэтому перед деплоем должен пройти `mvn verify` или CI. В этой среде не выполнялся платный вызов OpenAI и не использовался реальный Telegram-токен.

## Перенос бота на Local API

Логика бота находится в Java. Официальный Local Bot API — отдельный нативный процесс в соседнем контейнере.

Если токен уже использовался с облачным API, **один раз перед переключением** выполните с экспортированным `TELEGRAM_BOT_TOKEN`:

```sh
sh scripts/telegram-setup.sh logout-cloud
```

По умолчанию используется long polling, входящий публичный URL не нужен. Если раньше был webhook, после запуска Local API удалите его, сохранив ожидающие updates:

```sh
docker compose exec app sh -c 'curl --fail-with-body -sS -X POST "$TELEGRAM_BASE_URL/bot$TELEGRAM_BOT_TOKEN/deleteWebhook" --data-urlencode "drop_pending_updates=false"'
```

Не запускайте несколько Local Bot API для одного токена. Local API не публикуется наружу общим Compose.

Для webhook установите `TELEGRAM_MODE=webhook` и `TELEGRAM_WEBHOOK_SECRET`, затем зарегистрируйте URL `/telegram/webhook` через `setWebhook`. Скрипт поддерживает `webhook` с `TELEGRAM_WEBHOOK_URL`. Заголовок `X-Telegram-Bot-Api-Secret-Token` проверяется постоянным по времени сравнением. В polling-режиме этот endpoint отключён.

## Пакеты и интерфейсы

| Пакет | Содержание |
|---|---|
| `dto` | Неизменяемые данные и манифесты |
| `model` | Интерфейс Job и перечисления; Hibernate entity скрыта в `model.impl` |
| `repo` | Контракты работы с БД; Hibernate/SQL в непубличных `repo.impl` |
| `service` | Контракты Telegram, S3, OpenAI, FFmpeg и служебных операций |
| `config` | Типизированные env-настройки и конфигурация Spring |
| `controllers` | Контракт webhook; реализация в `controllers.impl` |
| `task` | Контракты обработчиков и runtime; реализации в `task.impl` |

Все реализации прикладных интерфейсов — package-private классы в `impl`. Между пакетами используются интерфейсы. Данные (`record`), перечисления, тип ошибки, Spring Boot entry point и настройки доступны как типы данных. Тест ArchUnit проверяет непубличность реализаций и отсутствие зависимостей на `impl` извне.

## Очередь и восстановление

Этапы: `UPLOAD → CONVERT → TRANSCRIBE → FORMAT → DELIVER`. У каждого — один последовательный executor. Разные этапы одновременно обрабатывают разные записи.

Состояния: `READY`, `RUNNING`, `RETRY`, `COMPLETED`, `FAILED`, `DELETED`.

- PostgreSQL хранит очередь и все подтверждённые переходы. FIFO среди готовых задач; отложенный retry временно пропускается.
- Захват: короткая транзакция с `FOR UPDATE SKIP LOCKED`; при внешних вызовах транзакция не удерживается.
- В отдельной таблице хранится lease каждого обработчика. Она ограничивает активную обработку этапа одним владельцем даже при нескольких экземплярах приложения.
- Heartbeat продлевает lease. Старый владелец после истечения lease не может подтвердить переход, checkpoint или отправку.
- Перезапуск восстанавливает текущий незавершённый этап после истечения lease. Успешные этапы не повторяются.
- Сначала сохраняется артефакт S3, затем переход в PostgreSQL. Ключи S3 включают task UUID и token попытки: устаревший обработчик не перезаписывает результат нового.
- Транскрибация сохраняет checkpoint после каждой части. Повтор начинает с первой неподтверждённой части.
- Доставка подтверждает отправленный TXT. После сбоя до подтверждения файл отправляется повторно со свежей ссылкой; после подтверждения — не повторяется.
- `update_id` уникален: повторная доставка одного Telegram update не создаёт вторую задачу. Курсор polling сохраняется в той же транзакции.
- Уведомления выполняются отдельно, с собственной задержкой повтора. Их сбои не перезапускают транскрибацию.
- Ошибки 429, 5xx, 408 и сетевые сбои повторяются с увеличением задержки. Остальные постоянные ошибки и исчерпанные попытки приводят к `FAILED`.

Внешние OpenAI/Telegram вызовы имеют семантику **at least once**: если провайдер принял запрос, а подтверждение потерялось, повтор может повторно списать стоимость или создать сообщение. Внутренний token предотвращает устаревшую запись в БД, но не отменяет уже принятый внешний запрос. При длительном сетевом зависании физические внешние вызовы старого и нового владельцев могут пересечься.

Команды: `/help`, `/status`, `/retry <uuid>`. Повторить можно только свою задачу со статусом `FAILED`. Завершённые задачи повторно не запускаются.

## Аудио и говорящие

FFmpeg извлекает первую аудиодорожку, формирует mono MP3. Запуски выполняются через `ProcessBuilder` без shell, с таймаутом. Сетевые протоколы входного медиа отключены. Ограничения размера, длительности, битрейта, таймауты и пути к бинарникам настраиваются env.

OpenAI вызывается через `/v1/audio/transcriptions`: `response_format=diarized_json`, `chunking_strategy=auto`, `language=ru` (зафиксирован в коде, не настраивается). Передаются байты файла, а не S3 URL.

По умолчанию запись делится на части до 20 минут с двухсекундным перекрытием. Размер каждой части дополнительно ограничен `OPENAI_MAX_UPLOAD_BYTES` (24 млн байт). Таймкоды пересчитываются в абсолютное время. Реплика в перекрытии включается по принадлежности её середины основной области части; граница всё ещё может влиять на распознавание.

Из отдельных реплик без наложения выбираются 2–8-секундные образцы, до четырёх голосов. Они передаются последующим частям через `known_speaker_names[]` / `known_speaker_references[]`. Только явно возвращённое имя известного голоса связывается между частями. Неизвестные метки получают отдельные номера: одинаковый `A` в разных ответах не считается одним человеком. Для больших встреч и коротких/перекрывающихся реплик один человек может получить несколько номеров. Автоматическое сопоставление требует проверки качества на реальных русских записях.

На 02.10.2026 OpenAI объявляет отключение `gpt-4o-transcribe-diarize` 26.02.2027. Адаптер отделён интерфейсом; имя модели — env. Смена имени сама по себе не гарантирует совместимость формата или поддержку диаризации.

## Хранение и уборка

`created_at` и `updated_at` генерирует PostgreSQL. `updated_at` обновляет `BEFORE UPDATE` trigger. Java не присваивает эти поля. Hibernate настроен строго на `ddl-auto=validate`; схему создают только ручные SQL-миграции Flyway.

Условие уборщика:

```sql
status = 'COMPLETED'
AND updated_at <= clock_timestamp() - interval '24 hours'
```

Интервал настраивается `RETENTION`, по умолчанию `24h`. Поля `delete_after` нет. `COMPLETED` ставится после отправки всех результатов. Уведомления, delivery receipts и lease уборщика живут в отдельных таблицах и не изменяют дату завершённой задачи.

Уборщик удаляет весь S3-префикс задачи (включая артефакты неудачных попыток), незавершённые multipart uploads, локальные рабочие файлы и загруженный файл Local API, если его не использует другая неудалённая задача. Только после успешной очистки ставится `DELETED` и удаляются JSON checkpoints. Если часть удаления не удалась, состояние и `updated_at` остаются прежними; следующий запуск повторяет идемпотентное удаление.

Незавершённые и `FAILED` задачи сохраняются **без автоматического срока удаления**, чтобы не потерять возможность восстановления. Это соответствует правилу «чистить только COMPLETED». Строки задач и метаданные остаются для диагностики. Служебный кэш/база TDLib не удаляются; приложение удаляет лишь отслеживаемые скачанные медиафайлы. Следите за свободным местом на volume Local API.

Для versioned bucket включите `S3_PURGE_VERSIONS=true` и разрешите `ListBucketVersions`/`DeleteObjectVersion`; без этого простое удаление оставляет версии. Не задавайте bucket lifecycle на все файлы через сутки от загрузки: он может удалить активную задачу. Уборщик должен иметь права List/Get/Put/Delete для префикса и List/AbortMultipartUpload. Bucket создаётся заранее.

S3 URL по умолчанию действует 24 часа с момента подписания. Временные AWS credentials могут закончиться раньше. Дата истечения URL отличается от физического удаления файла. При остановленном сервисе очистка возобновится после запуска. Копия TXT в Telegram не удаляется уборщиком.

## Проверки

```sh
mvn verify
```

Нужны JDK 17+, Maven, FFmpeg/ffprobe и Linux/macOS. Тестовый PostgreSQL запускается автоматически через embedded-postgres; Docker не требуется. PostgreSQL нельзя запускать от root, поэтому тесты выполняются обычным пользователем. GitHub Actions уже настроен.

Тесты используют настоящие PostgreSQL, Flyway, Hibernate и FFmpeg. Внешние Telegram/OpenAI/S3 заменяются тестовыми адаптерами; HTTP multipart проверяется локальным HTTP-сервером. Проверяются дубликаты updates, параллельный захват, восстановление lease, запрет устаревших записей, ошибки и повторы, 24-часовая очистка, скрытые реализации и полный маршрут большого видео с искусственными сбоями.

После развёртывания проверьте голосовое, видео больше 20 МБ и запись с несколькими говорящими. Затем остановите контейнер во время конвертации/транскрибации и убедитесь, что после запуска задача продолжилась. Health endpoint проверяет доступность приложения/БД, но не качество распознавания или действительность внешних ключей.
